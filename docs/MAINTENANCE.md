# 维护策略

## 会不会拖慢更新？

会增加单次改动的固定成本，但不应增加太多等待时间。当前目标是让 PR 自动检查在几分钟内结束，把真实 RabbitMQ 容器测试移到每周或高风险改动时运行。

流程的收益不是“永远没有 bug”，而是：

- 让失败在合并前出现，而不是演示或客户环境中出现
- 让诊断规则变化有 diff、测试和回滚记录
- 避免快速试错变成无法解释的行为漂移
- 让未来的第二位维护者能够接手

## 当前门禁

每个 PR 必须通过：

- Python 3.9 和 3.12 单元测试
- Python 编译检查
- 浏览器 JavaScript 语法检查
- 无真实 RabbitMQ 依赖的 Web/API 冒烟测试

每周或手动运行：

- RabbitMQ 4.1 Management API 实时采集
- 制造无人消费积压并验证诊断结果

## 何时增加流程

只有出现相应风险时才增加：

- 第一位生产客户：要求至少 1 个非作者批准，高风险变更必须集成测试
- 多版本兼容：增加 RabbitMQ 版本矩阵
- 公网部署：增加认证、CSRF/SSRF 测试、依赖扫描和部署审批
- 自动修复：增加权限隔离、dry-run、审计日志和人工批准测试

## 何时删除流程

连续四周没有发现缺陷、却明显增加等待时间的检查，应重新评估或合并。流程本身也需要用数据证明价值：PR 等待时间、失败率、回滚次数和生产回归数量。
