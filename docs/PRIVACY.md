# 快照隐私与威胁模型

RabbitMQ Guard 的脱敏功能用于在客户本机生成可诊断、可复测的伪名化快照，降低向顾问或供应商交付数据时暴露生产标识符的风险。它不把快照变成匿名数据，也不能代替客户的数据分级、审批和保留策略。

## 保护目标

假设原始快照和脱敏密钥只存在于客户信任的本机或执行环境中，接收方只能拿到脱敏后的 JSON。目标是让接收方不能从输出中直接读出：

- Management API 地址和集群名
- 节点、vhost 和队列名
- quorum 成员和 leader 名称
- 连接名、RabbitMQ 用户名和客户端名
- 队列参数、合成案例说明和未识别字段

不在保护范围内：已经控制客户主机或进程的攻击者、同时获得密钥和输出的接收方、运行内存取证，以及通过其他渠道掌握足够业务上下文后的关联推断。

## 转换方式

标识符使用 `HMAC-SHA256(key, category + value)` 生成 16 位十六进制伪名。不同类别使用不同的输入域；相同密钥和原值会得到相同伪名，因此两次快照中的节点成员、queue leader 和目标对象仍可对应。

输出采用字段白名单，不会先复制完整输入再尝试删除。当前保留：

- 集群、节点、队列、连接和活动的诊断数值及布尔状态
- queue 类型、运行状态以及 quorum 成员关系
- 合法的采集时间戳
- 脱敏算法、伪名长度和稳定性说明等非秘密元数据

`scenario`、`queues[].arguments` 和所有未知字段会被删除。无法识别的枚举被改为 `unknown`，无法解析的时间戳、非有限数值和类型错误的指标被改为 `null`。已经脱敏的快照会被拒绝，避免二次伪名化破坏跨次对应关系。

## 密钥要求

- 密钥只能通过环境变量提供，不能作为命令行明文参数。
- 程序最低接受 16 个 UTF-8 字节；长度不等于随机性，生产使用推荐 32 个随机字节。
- 基线和复测必须使用同一密钥，否则同一对象会得到不同伪名，无法可靠对比。
- 密钥应保存在客户控制的密钥管理系统中，不要提交到 Git、Issue、报告、终端录屏或工单。
- 怀疑密钥泄漏时应轮换密钥并重新生成需要保留的脱敏快照。轮换后旧、新快照不能直接做对象级对比。

## 残余敏感信息

为保证诊断有效，以下信息仍存在于脱敏输出中：

- 采集时间
- 连接、channel、队列和消费者数量
- 消息存量、未确认消息、吞吐和重复投递速率
- 节点资源使用量、告警状态和在线状态
- 集群规模、queue 类型、成员数量及在线成员关系
- 同一密钥下对象是否相同，以及对象在多次快照间的变化

这些数据可能暴露业务高峰、容量、故障窗口和架构规模。短队列名等可猜测标识在密钥泄漏后也可能被字典枚举。任何公开发布或跨客户合并分析都需要额外评估。

## 交付前检查

1. 在客户信任的环境中运行 `sanitize` 或 `collect --sanitize`，不要把原始快照先发送到外部环境。
2. 使用 `diagnose` 在本机验证脱敏快照仍能产生预期结果。
3. 打开脱敏 JSON，确认 `capture.kind` 为 `sanitized`，并搜索客户名、域名、IP、用户名和已知队列名。
4. 只交付脱敏 JSON；不要一并交付 shell 历史、环境转储、原始报告、SQLite 数据库或密钥。
5. 在工单中记录接收方、用途、保留时间、删除时间和所用密钥版本，不记录密钥值。

使用 `deliver` 时，以上第 2-4 步由固定格式交付包和生成后的自校验完成；客户仍应通过独立渠道发送命令输出的 ZIP SHA-256，并执行组织内部审批。接收方运行 `verify-delivery` 只能证明收到的文件内部一致且符合当前格式，不能证明文件来自特定客户。

工作台显示“已脱敏”只表示输入声明为 RabbitMQ Guard 的脱敏格式，不是对任意上传文件做独立合规认证。
